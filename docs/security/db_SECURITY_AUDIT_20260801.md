## 🔴 P0 — 严重问题

### P0-1: 零认证对外开放完整 CRUD（依赖 127.0.0.1 网络隔离）
- **位置**: `dbv2.py` L180、L191-196、L323-406
- **当前状态**: ⚠️ 部分修复
  - ✅ 默认监听 `127.0.0.1`（`dbv2.py` L180），Docker 也绑定到 127.0.0.1
  - ✅ 配置通过 confs + 环境变量两层加载，配置完整性校验（`dbv2.py` L118-129）
  - ❌ 仍无任何认证机制（`RpcServer` 无 auth 回调）
  - ❌ SELECT 无默认 LIMIT：`_do_select` (L364-366) limit 参数可选，客户端可省略以获取全表数据
  - ❌ UPDATE/DELETE 不强制要求 WHERE：`_do_update` (L391-394) 和 `_do_delete` (L400-403) 仅在 where_cond 非空时添加 WHERE 子句，可执行无条件全表更新/删除
  - ❌ 无表级/操作级权限控制
- **修复建议**:
  1. ~~确保管理接口仅监听 127.0.0.1~~ ✅ 已实现
  2. 添加 API Token 认证（预共享密钥，所有调用需携带 `_auth` 字段）
  3. SELECT 强制添加 LIMIT 上限（默认 1000 条），防止拖库
  4. 添加操作权限：日志写入只允许 insert，禁止 delete/truncate
  5. 拒绝无条件 UPDATE/DELETE（必须带 where 条件）
  6. DDL 操作仅限本地运维工具，RPC 接口完全禁用

## ✅ 已有安全机制

1. ✅ **SQLAlchemy Core 参数化查询**：核心 CRUD 路径使用表反射 + 参数化，零 SQL 注入风险 (`dbv2.py` L346-406)
2. ✅ **仅监听 127.0.0.1**：不对外暴露 (`dbv2.py` L180)
3. ✅ **集中式日志 fail-safe**：db 不可用时静默丢弃，不阻塞业务 (`example_log_client.py` L57-106)
4. ✅ **自动提交/回滚**：异常时自动回滚事务
5. ✅ **日期/时间适配**：ISO 8601 处理，`"$now"` 哨兵 (`dbv2.py` L242-287)
6. ✅ **日志自动清理**：后台线程按时间+条数清理，防止磁盘占满 (`dbv2.py` L480-528)
7. ✅ **log_client 健壮性**：异步队列、后台线程、fail-safe、队列上限 10000 (`example_log_client.py` L38-41)
8. ✅ **配置白名单校验**：`_merge_ini` 仅覆盖已知 section/key，防止意外字段注入 (`dbv2.py` L73-81)
9. ✅ **配置完整性校验**：启动时检查所有必需配置项，缺失则退出 (`dbv2.py` L118-129)
10. ✅ **SQLite PRAGMA 优化**：WAL 模式 + NORMAL 同步 + busy_timeout + mmap (`dbv2.py` L139-155)
11. ✅ **表反射线程安全**：double-check 锁机制防止并发反射竞态 (`dbv2.py` L225-239)
